# Deploying InterAct

The demo runs as **one free Render web service** built from the `Dockerfile`: the backend serves the API under `/api` and the built web app everywhere else, so everything is on one `https://` address. There's no CORS, no cross-site cookie, and no proxy that could time out while the service wakes up. The database is **Neon** (free PostgreSQL) and the model is a hosted, OpenAI-compatible API (**Groq** by default).

You need three free accounts: Neon, Groq and Render. You also need to update the Google and GitHub OAuth apps. Secrets go only into the Render dashboard, never into the repository or a chat.

## What the free plans mean for the demo

Checked in November 2026; plans change, so confirm in each dashboard.

| Service | Free plan | What it means for InterAct |
|---|---|---|
| Render web service | Sleeps after 15 minutes without traffic, then takes about a minute to wake. 750 hours a month. The disk is wiped when it sleeps or restarts. | The first visit after a quiet spell is slow. Uploaded files are lost when it sleeps, but their text, topics and questions are already in the database, so interviews still work; only "process again" asks for a new upload. |
| Neon | 1 GB of storage and 100 compute-hours a month per project. Sleeps after 5 minutes idle. | Plenty for a demo. The first query after a pause takes a moment; the app checks connections before use. |
| Groq | Free models (for example gpt-oss and Qwen) reportedly allow about 30 requests a minute and 1,000 a day. The Llama 3.x models reportedly left the free plan in August 2026. | One 5-question interview makes roughly 30–40 model calls, so about 25 interviews a day. `STYLE_CHECK=rules` saves one call per question. |

## 1. Neon: the database

1. Sign up at [neon.com](https://neon.com) and create a project, for example `interact`, in a region near you.
2. On the project dashboard, open **Connect**, choose the **pooled** connection, and copy the connection string. It looks like `postgresql://user:password@ep-....neon.tech/neondb?sslmode=require`.
3. Keep it for step 3. Don't paste it anywhere else. The app accepts it as given and adds the driver itself. Migrations run automatically every time the service starts.

## 2. Groq: the model

1. Sign up at [console.groq.com](https://console.groq.com) and create an API key under **API Keys**. Copy it now: it's shown once.
2. Open **Limits** (or **Models**) and choose a chat model your plan includes. Note its exact id, for example `openai/gpt-oss-20b`.
3. The prompts were tuned on Llama 3.1 8B. After deploying, run one short interview and check the reactions and the report. If replies come back malformed, try another free model; the app retries once, then shows "try again" instead of making anything up.

## 3. Render: the service

1. Sign up at [render.com](https://render.com) with GitHub, and give Render access to `avaneja/interAct_main_2026`.
2. Choose **New → Blueprint**, pick the repository, and select the branch to deploy. `render.yaml` describes one free web service called `interact`.
3. Render asks for the values marked `sync: false`:

   | Variable | Value |
   |---|---|
   | `DATABASE_URL` | The Neon connection string from step 1 |
   | `PUBLIC_URL` | `https://interact.onrender.com`, the service address Render shows (if `interact` is taken it adds a suffix), with no trailing slash |
   | `LLM_MODEL` | The Groq model id from step 2 |
   | `LLM_API_KEY` | The Groq API key |
   | `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET` | From step 4 |
   | `GITHUB_CLIENT_ID`, `GITHUB_CLIENT_SECRET` | From step 4 |

   `SESSION_SECRET` is generated by Render. `APP_ENV=production` is set in the image, and the app refuses to start without an `https://` `PUBLIC_URL`, a real model provider and a strong session secret.
4. Deploy. The first build takes several minutes: it builds the web app, installs the backend and runs the migrations. When the service is **Live**, open `PUBLIC_URL/api/v1/health`; it should say `{"status":"ok"}`.

## 4. Sign-in for the deployed address

Each provider must know the deployed callback address, exactly:

| Provider | Callback URL |
|---|---|
| Google | `https://<your service>.onrender.com/api/v1/auth/google/callback` |
| GitHub | `https://<your service>.onrender.com/api/v1/auth/github/callback` |

- **Google:** in the existing OAuth client, add the address above under *Authorised redirect URIs*, and add `https://<your service>.onrender.com` under *Authorised JavaScript origins*. While the consent screen is in *Testing*, only listed test users can sign in.
- **GitHub:** an OAuth app has one callback URL, so create a second app (for example *InterAct demo*) with the homepage and callback above, and use its client id and secret on Render. Your local app keeps the development one.

Put the four values into Render's environment settings and redeploy.

## 5. Check the demo

1. Open `PUBLIC_URL` in Google Chrome (speech recognition needs Chrome itself, not an editor preview).
2. Sign in with Google and with GitHub.
3. Run a short topic interview with **Adaptive** on, then one with it off. The report shows which mode ran.
4. Upload a short PDF and run a document interview; the report should show "Grounded in your document".

## Updating the demo

Pushing to the deployed branch redeploys automatically. Migrations run on start, so schema changes apply themselves. To roll back, choose an earlier deploy in Render's **Events**.
